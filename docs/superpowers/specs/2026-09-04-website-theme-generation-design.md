# Website Theme Generation — Design Spec

Status: Approved by user in brainstorming chat. Ready for implementation planning.

## Motivation

GameForge generates pixel art via Pixellab, all organized around Style
Bibles — a shared aesthetic description ("dark fantasy, parchment and
iron") that every generation drawn from it stays consistent with. This
feature extends that same model to a second, unrelated output type:
website design tokens (CSS custom properties), generated by Claude
instead of Pixellab, reviewable and promotable through the exact same
Jobs queue the pixel-art pipeline already uses.

The two output types share nothing at the API/content level (different
provider, different content — an image file vs. a small CSS file) but
share everything at the *workflow* level: describe an aesthetic once in a
Style Bible, generate one or more candidate results from it, review each
one, promote the keeper or discard and retry. This spec is entirely about
wiring a second generator into that existing workflow shape, not about
building a second workflow.

## Out of scope for V1

- **No component-level CSS.** Claude generates design *tokens* only —
  colors, typography choices, a spacing scale, radius values — as CSS
  custom properties. It does not generate button/card/nav CSS rules.
  Simpler and more reliable (no risk of Claude producing broken layout
  CSS), and more genuinely portable — the output is just variables, so it
  drops into any project's own component structure rather than assuming
  one. GameForge's own sample page (see "Review and promotion" below) is
  the one place with fixed, hand-authored component CSS, purely to have
  something concrete to preview tokens against.
- **No target-project integration.** The output is generic, portable CSS
  custom properties with no assumptions about any specific project's
  framework, class names, or HTML structure. GameForge does not know
  about, read from, or write into any other codebase (including this
  project's own portfolio sites).
- **No multi-candidate generation.** One job produces one result. If you
  don't like it, Retry (already an existing job action) generates a new
  one. Not generating 3 variations up front to choose between — that's
  3x the cost for something Retry already covers more cheaply.
- **No live theme editing.** You can't tweak a generated token value by
  hand in GameForge and re-preview — you review what Claude produced,
  and promote or discard. If a value is wrong, retry with a more specific
  prompt, or hand-edit the promoted CSS file after the fact, outside
  GameForge.
- **No multi-turn refinement.** Each job is a single, one-shot Claude
  call. No "make the accent color warmer" follow-up conversation within
  GameForge — that's a distinctly bigger feature (would need to store and
  resend conversation history per job) and isn't what was asked for here.

## Data model

Two changes, both additive — no renamed or removed columns, matching
this project's established pattern for extending `jobs`/`assets` (see
`nine_slice_margins`/`states`/`source_job_id` from the UI Sheets
feature).

Migration NNN (exact number set at plan time — this project is at 007 as
of this feature's own predecessor, Edit in Aseprite):

```sql
ALTER TABLE jobs ADD COLUMN output_kind TEXT NOT NULL DEFAULT 'image';
ALTER TABLE assets ADD COLUMN output_kind TEXT NOT NULL DEFAULT 'image';
```

`output_kind` is `'image' | 'theme'`. This is the **structural**
discriminator the worker and dashboard branch on — not `asset_type`
(which, per this project's established principle from the UI Sheets
feature, is display-label-only and never string-matched for routing) and
not the prompt text. It's set explicitly, once, at job-creation time by
whichever UI action created the job (the existing "Generate" page always
writes `'image'`; a new theme-generation action always writes `'theme'`),
and never inferred or guessed anywhere downstream.

`jobs.result_path` / `assets.image_path` (unrenamed — a bigger rename
would touch code across the whole app for no behavioral benefit) hold a
`.css` filename under `storage/themes/` for a theme job/asset, exactly
the same way they hold a `.png` filename under `storage/images/` for an
image job/asset today. Every place that currently treats `image_path` as
"the file for this row" keeps doing exactly that — the only new thing is
*which subdirectory and extension* it points to, decided by
`output_kind`, not by sniffing the filename.

**Storage split, not shared:** `storage/themes/` is a new sibling
directory to `storage/images/`, not a shared bucket — theme files and
image files never collide on filename, and existing image-specific
logic (`storage/images/[filename]/route.ts`'s content-type map, orphan
cleanup, etc.) stays untouched and unaware theme files exist at all.
Theme-specific serving/cleanup logic is new, parallel code, not a
generalization of the image code.

## Generation mechanism

New service, `ThemeGenerator`, structurally parallel to the existing
`ImageGenerator`/`getImageGenerator()` (mock-vs-real lazy singleton,
picked by whether a real API key is configured — here `ANTHROPIC_API_KEY`
instead of `PIXELLAB_API_KEY`). A `MockThemeGenerator` returns a fixed,
valid token set instantly (for tests and for running the full pipeline
without spending real API calls, exactly matching `MockGenerator`'s
existing role for pixel art). `AnthropicThemeGenerator` calls the real
Anthropic Messages API.

**Direct `fetch`, not the `@anthropic-ai/sdk` package.**
`PixellabGenerator` already calls Pixellab's REST API via plain `fetch`,
not a vendor SDK — same reasoning applies here: this project avoids
dependencies where a REST call plus a Zod-validated response does the
job, and `POST https://api.anthropic.com/v1/messages` is a plain HTTP
call like any other.

**Structured output via forced tool use.** The request forces Claude to
respond with exactly one tool call (`tool_choice: { type: 'tool', name:
'emit_theme' }`) whose input schema is the token shape below — this is
the reliable way to get parseable structured output from Claude, instead
of asking for JSON in prose and hoping the response doesn't wrap it in
markdown fences or commentary.

```typescript
// The tool's input_schema (JSON Schema, sent to Anthropic) and the
// matching Zod schema (used to validate the tool_use block's `input`
// once it comes back) describe the same shape:
const ThemeTokensSchema = z.object({
  colorBackground: z.string(),   // any valid CSS color
  colorForeground: z.string(),
  colorAccent: z.string(),
  colorBorder: z.string(),
  fontHeading: z.string(),       // a font-family value, e.g. "'Cinzel', serif"
  fontBody: z.string(),
  spaceUnit: z.string(),         // e.g. "8px" — base unit the sample page's spacing multiplies
  radiusBase: z.string(),        // e.g. "4px"
});
```

The prompt includes the Style Bible's `parameters` (the same aesthetic
description already used for pixel-art generation) plus the job's own
`prompt` field (any additional per-generation direction, exactly
mirroring how pixel-art jobs already combine Style Bible parameters with
a per-job prompt). The response's validated token values get written out
as a real CSS file:

```css
/* storage/themes/<uuid>.css */
:root {
  --color-bg: #1a1420;
  --color-fg: #f0e6d2;
  --color-accent: #e8a33d;
  --color-border: #4a3728;
  --font-heading: 'Cinzel', serif;
  --font-body: 'EB Garamond', serif;
  --space-unit: 8px;
  --radius-base: 4px;
}
```

If Claude's response doesn't include a valid tool call, or the tool
call's input fails `ThemeTokensSchema.safeParse`, the job fails closed
(`status = 'failed'`) with the validation error logged server-side —
matching this project's established pattern of hard-failing on a
malformed generation result rather than guessing or defaulting.

## Worker integration

`worker.ts`'s `processJob` branches on `job.output_kind`, structurally,
right alongside its existing `isUiSheet` branch:

```typescript
if (job.output_kind === 'theme') {
  result = await getThemeGenerator().generate(job.prompt, job.style_id);
} else if (isUiSheet) {
  result = await getImageGenerator().generateUiAsset(...);
} else {
  result = await getImageGenerator().generate(job.prompt, job.style_id);
}
```

Both generator lazy-singletons stay fully independent — which pixel-art
generator is active (mock vs. real Pixellab) and which theme generator is
active (mock vs. real Anthropic) are two unrelated axes, each driven by
its own env var's presence, exactly like today's single axis.

## Generation entry point (UI)

A new action alongside the existing "Generate" page — reuses the same
Style Bible picker component (`StyleBiblePicker`, already extracted and
shared as of the UI Sheets feature) plus a prompt field, but writes a job
with `output_kind: 'theme'` instead of `'image'`. Whether this lives as a
second tab/section on the existing Generate page or its own page (mirroring
how UI Sheets got its own `/dashboard/ui-sheets` page rather than a mode
switch on Generate) is a plan-level layout decision, not a data-model one
— either way, it POSTs to the same underlying job-creation path with a
different `output_kind`.

## Review and promotion

The Jobs page already lists every job regardless of type. For a
`output_kind: 'theme'` job, instead of the existing `<img>` thumbnail, the
job card renders an `<iframe>` containing a **fixed, GameForge-authored
sample page**: a heading, a paragraph, a primary button, a secondary
button, a card, and a small nav bar, all styled purely via `var(--...)`
references into the token set above. The generated theme's `.css` file is
injected as that sample page's stylesheet, so the same fixed markup
renders differently per theme — this is the live preview.

**The `<iframe>` isn't a UI nicety, it's load-bearing.** The generated CSS
sets its tokens on `:root` (see the example file above) — if that
stylesheet were injected directly into the Jobs page's own DOM (a `<style>`
tag, a CSS-in-JS `<style jsx>` block, anything sharing the document with
the rest of the dashboard), its `:root` rules would apply to the *entire
page*, silently overriding GameForge's own theme variables (`--accent`,
`--bg`, `--ink`, etc. — the ones this app's own `globals.css` already
defines) for as long as that job card is mounted. An `<iframe>` gets a
genuinely separate document, so the generated `:root` only ever affects
that iframe's own contents — the one isolation mechanism that actually
prevents a generated theme from visually corrupting the rest of the
dashboard around it while it's being reviewed.

Promote/Discard/Retry work exactly as they already do for image jobs.
Checked the existing promote route (`app/api/assets/from-job/route.ts`)
directly: promoting an image job never copies or moves the file — it
just inserts a new `assets` row whose `image_path` is set to the SAME
`job.result_path` string the job already wrote to. Theme promotion works
identically, with one addition: the new `assets` row's `output_kind` is
copied from `job.output_kind` (currently the INSERT hard-codes neither
column's value, since `output_kind` doesn't exist yet — this is a
one-line addition to that route's column list). No new file-handling
logic — the `.css` file stays exactly where the job wrote it, under
`storage/themes/`, referenced by filename from both the job row and,
after promotion, the asset row, the same double-reference pattern
`storage/images/` filenames already have.

The Assets grid gains the same treatment: a small rendered preview (the
same fixed sample page, smaller) instead of an image thumbnail, for any
`output_kind: 'theme'` asset.

## Error handling

Every failure mode is a distinct, specific job failure with a logged
reason server-side, matching this project's established pattern:
- Anthropic API call fails outright (network, auth, rate limit) → job
  `failed`, error logged.
- Response has no valid `emit_theme` tool call → job `failed`, logged as
  a malformed-response case (distinct log line from the API-call-failed
  case, so which one happened is diagnosable from the worker log alone).
- Tool call's `input` fails `ThemeTokensSchema.safeParse` → job `failed`,
  the specific Zod validation error logged (which field, what was wrong).
- Writing the resulting `.css` file fails (disk full, permissions) →
  wrapped in try/catch with `console.error` per this project's
  fs-operation rule, job `failed`.

## Testing

- `ThemeTokensSchema` parsing and the prompt-construction logic (Style
  Bible parameters + job prompt → the actual request sent to Anthropic)
  are pure functions, unit-testable without a network call.
- `AnthropicThemeGenerator`'s actual `fetch` call is tested with a mocked
  `fetch`, mirroring exactly how `PixellabGenerator`'s tests already mock
  `fetch` for Pixellab — this project's established pattern for "the
  external HTTP boundary is the one thing that's mocked, everything else
  runs for real."
- `MockThemeGenerator` returning a valid, fixed token set means the full
  pipeline (job creation → worker pickup → file write → job complete →
  Jobs page preview render → promote → Assets page preview render) is
  exercisable end-to-end in tests and in local dev without spending a
  real Anthropic API call, exactly matching how `MockGenerator` already
  serves that role for pixel art.
- The sample preview page's actual visual rendering is not something an
  automated test can meaningfully assert on (same reasoning this
  project already applied to "does Aseprite actually open with the
  right file" and "does the generated pixel art actually look good") —
  verified manually, once, against a real Anthropic API call, the same
  discipline as every prior feature's end-to-end walkthrough.

## Security note

The Anthropic API key is a new secret (`ANTHROPIC_API_KEY`), configured
the same way `PIXELLAB_API_KEY` already is — read server-side only
(worker process), never exposed to the browser, never logged. No new
trust-boundary concerns beyond what pixel-art generation already has:
the job's `prompt` field reaches an external API call exactly like it
already does for Pixellab, and the response is Zod-validated before any
of it reaches disk — the same shape of validation this project already
applies everywhere a network response crosses into local state.
